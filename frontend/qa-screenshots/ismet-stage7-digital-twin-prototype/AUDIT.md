## Honest limitations of this evidence set

- **Mobile 390×844 and real 200% browser zoom were NOT captured.** The connected browser's window could not be resized in this remote session (`resize_window` reported success but the actual rendered viewport never changed from ~1568×745 in any subsequent screenshot) — a genuine environment constraint, not something this session could work around. `MOBILE_390X844_PASSED` and `REAL_200_PERCENT_ZOOM_PASSED` are reported `NO` for this reason, not inferred as passing.
- **Front/Left/Right/Back views, chest-module focus, and wrist-module focus were exercised interactively during this session** (visually confirmed correct — deterministic view switching, region-focus ring following the selected module, no clipping) **but not all individually saved as separate evidence files**, given the volume of manual browser round-trips this environment's software-rendered VM required per capture (each `Page.captureScreenshot` call took several seconds to tens of seconds due to slow WebGL/shader compilation under VMware's software 3D renderer). What is captured is a representative, real, inspected subset proving the mechanism works end-to-end (selection, region-focus, deterministic view switching, WebGL failure/recovery) rather than an exhaustive per-view/per-region screenshot matrix.
- **Real OS screen-reader testing was not performed**, per the master prompt's own explicit instruction to defer it (`ACTUAL_SCREEN_READER_STATUS: DEFERRED_BY_OWNER_UNTIL_AFTER_STAGE7_INTEGRATION`).
- **Keyboard-focus-ring visibility was attempted via simulated Tab/Enter key presses** but could not be conclusively confirmed via automated screenshot in this session (the automated key events did not reliably reproduce the exact focus state a real user's Tab key would). The `:focus-visible` CSS rules exist in `stage7Prototype.css` for every interactive control and were verified by code review, not by a passing automated keyboard screenshot test. `KEYBOARD_ACCEPTANCE_PASSED` is reported honestly reflecting this partial verification — see `MASTER_HANDOFF_REPORT.md` §15 for the exact breakdown.
- One genuine, tool-side artifact was encountered and corrected during this session: two early screenshot captures (`save_to_disk`) returned byte-identical file content despite being taken at different points with visually different on-screen state, and separately, the dev server's HMR state became corrupted mid-session (an unstyled "reader mode"-like render) — both required deleting the affected evidence, restarting the dev server with a cleared build cache, and recapturing cleanly. The final 6 files listed above are the clean, correctly-distinct recapture; no image with a hash collision or corrupted render was retained.

## Real, reproduced material self-review finding

The prototype's FIRST material/lighting pass (before this evidence was captured) rendered the figure legible only when a screenshot was zoomed in — at full-page scale it collapsed into the dark stage background, reproducing by accident the exact silhouette weakness (`CURRENT_SYSTEM_AUDIT.md` F1) this prototype exists to fix. This was caught via direct visual inspection during this session (not assumed), and fixed by brightening `stage7BodyMaterial`/`stage7JointMaterial` and the key/rim light intensities in `stage7PrototypeMaterials.ts` / `Stage7Lighting.tsx`. All 6 evidence images above reflect the corrected, brighter treatment.
